A project to build and train a neural network to solve a Rubik's cube using a Lego robot.

Many people can learn to solve a Rubik's cube in a couple of hours. Doing so involves recognising a few key patterns, learning 6 or 7 simple algorithms and practice. Taken to extremes, the global speedcube circuit includes numerous youngsters who can solve a scrambled cube in under 4 seconds, with 9-year-old Teodor Zajder from Poland setting a 2.76-second world record on 8 February 2026.

Source: Guinness — Teodor Zajder, 8 February 2026

It might be surprising then, to discover that a Rubik's cube falls into a category of problems that people can solve using learned algorithms, but that is challenging for a learning system starting without a solving strategy.

Why? Because a scrambled Rubik's cube has 4.3 x 10^19 (43 quintillion) possible states. That is an unfathomably large number; it is more than the number of seconds that have passed since the big bang, and, assuming a 57 mm cube laid one face down, enough cubes to cover the Earth’s surface roughly 275 times.

The focus of this project and article is the neural network, training and most importantly, learning (both machine and personal!), so let’s get one of the coolest elements of the project out of the way first.

The Lego Robot

The robot is the incredible creation of David Gilday, an engineer at ARM and robot enthusiast. The build is based on Lego Set 51515 – Mindstorms Robot Inventor, a set which I fortunately bought for my son Henry a few years ago. The instructions provided with the Mindcuber build are good, so the robot was built, calibrated and performing its tricks to the amazement of my family in under 3 hours.

The base controller runs MicroPython and the mindcuber project includes a neat programme which scans the cube using a colour recognition sensor, computes the required moves to solve, then executes by rotating the cube in a basket, flipping as needed so that the required face can be rotated. The only notable limitation is that the robot can only rotate a single face (the face in the basket).

If you are interested in building MindCuber, you can find the instructions at https://mindcuber.com/.

The Neural Network

With the baseline robot built and tested I could move onto the project itself. In previous projects I have used various models in different ways, but this was my first attempt at creating one from scratch. The intention, apart from being very cool in its own right, is that it is the next logical stepping stone on the learning path to building my own LLM on the DGX Spark.

The network architecture

The first step is to create structure around the problem. For the Rubik’s cube this is straightforward and there are only 3 key things to define:

  • What does the input look like?
  • What does the network need to output?
  • What does correct mean?

The input to the network is simple: a current state representation of the cube. A 3x3 Rubik’s cube has 6 different colours, 6 faces and 9 stickers per face, this gives 324 values which will act as input to the network. These need to be encoded as numbers and shaped into a tensor. I used one-hot encoding: each colour is represented as a 6-digit array of zeros and ones. For example:

[0, 0, 1, 0, 0, 0] -> position 2 is true, colour = yellow
[0, 1, 0, 0, 0, 0] -> position 1 is true, colour = blue

Using one-hot is important where all inputs have general equality outside of their single defining attribute. If we used normal denary numbers (1, 2.. 6) the network may incorrectly think that the colour ‘6’ is more important than the colour ‘1’, or that colour ‘2’ is more like colour ‘1’ than colour ‘6’.

Our input tensor is therefore shape: (54, 6). That is, 54 rows (one per sticker), 6 columns (one per possible colour), which is then flattened to (324,), a continuous array of 324 values, most of which are 0 and 54 of which are 1.

def get_state_onehot(self) -> np.ndarray:
    """Return one-hot encoded state (54 positions x 6 colors = 324)."""
    onehot = np.zeros((54, 6), dtype=np.float32)
    flat = self.state.flatten()
    for i, color in enumerate(flat):
        onehot[i, color] = 1.0
    return onehot.flatten()

Although the input index of each value always refers to the same physical sticker position, we do not supply explicit 3D coordinates or hand-written solving rules. The fixed sticker order and training moves still encode the cube’s structure indirectly.

For the output we need 2 things; the next best move and the estimated number of moves remaining until the cube is solved. These are the Policy Head and Value Head respectively.

This model uses 12 quarter-turn moves on a Rubik’s cube. These are normally written as F (turn front face clockwise), F’ (front anticlockwise), etc. The Policy Head therefore outputs 12 raw logits. At inference time, these are normalised using softmax as probability scores which add up to 1.

Source: Rokicki and Davidson — 26 quarter turns, 20 half turns

So our policy head output tensor is shape: (12,). Ignore the 256 for now!

# Policy head: predicts best move (12 possible moves)
self.policy_head = nn.Sequential(
    nn.Linear(backbone_output_size, 256),
    nn.ReLU(),
    nn.Linear(256, 12)
)

The value head is given as a single value, shape: (1,)

# Value head: predicts distance to solved
self.value_head = nn.Sequential(
    nn.Linear(backbone_output_size, 256),
    nn.ReLU(),
    nn.Linear(256, 1)
)

The final step is to define the loss functions, one each for the value head and policy head. This answers the question about ‘what does correct mean?’.

For the value head (number of moves remaining) there are a number of options that would work, and I used mean squared error. This is calculated as

Value Loss = (predicted_distance − target_distance)²

For example, if the network predicts that the solved state is 5 moves away, but the target distance is 8 moves, then the Loss = (5 − 8)² = 9. The use of the quadratic function penalises large errors and encourages the network to be more accurate.

For the policy head, the standard approach in machine learning for a multi-class classification (the 12 possible moves) is to use cross-entropy. For a one-hot target, it penalises low probability assigned to the labelled move. This is computed as

Policy Loss = -log(probability_of_labelled_move)

For example if the labelled move is F’ and, (using the table above) the network predicts F’ 0.22, then the Loss = -log(0.22) ≈1.51. If it had predicted F’ 0.90, then Loss = -log(0.90) ≈0.10 (a much better score, suggesting that the network is accurate). If it had predicted F’ 0.01 then Loss = -log(0.01) ≈4.61 (a high loss for this labelled move; other moves may also lead to a solution).

During training of the network, total loss = value_loss + policy_loss.

Each fully connected layer in this network is a row of neurons, each of which takes every value from the previous layer, multiplies it by its own weight, adds them all up, adds a bias and outputs a single number.

The network will have 324 input values. Choosing the correct configuration of the remaining layers however, is not formulaic and is largely down to looking at other networks and experimentation. The successful configuration for this network came on the 3rd attempt, a number of weekends into the project.

The next few paragraphs warrant at least a full article in their own right, but I will try and capture the key elements of the configuration.

The successful network comprised an input projection, four residual blocks, an output projection and two heads, with 15 linear layers in total, with a common backbone and a total of 44.6m parameters.

The backbone uses Linear (the weighted sum), BatchNorm (normalise activations), ReLU (zero out negatives) and Dropout (randomly zero 10% of activations during training). The two heads shown above use Linear → ReLU → Linear; their final outputs are left as raw values.

Layer 1 (Input Projection) – in the first layer 324 input values is immediately expanded to 4096 neurons. That means 4096 neurons, each with their own set of 324 weights, receiving all of the 324 inputs, performing a multiplication, adding a bias and then outputting a single number. So (4096 neurons × 324 weights each) + 4096 bias values = 1,331,200 parameters at the first step.

BatchNorm is then run on the 4096 values to normalise each feature across the batch, before a learned scale and shift. At inference it normally uses running statistics. This stabilises the network, as a wide range of values would cause significant drift between the layers during training.

Source: PyTorch — BatchNorm1d

The next step is ReLU. Rectified Linear Unit is the most simple function in the code. If the output number is positive, it passes to the next layer, if it is negative, it is set to zero. This stops the network from becoming a simple set of linear calculations. Specifically, a sequence of affine layers without nonlinearities can be combined into one affine transformation, even when the intermediate widths differ. ReLU breaks this by zeroing out negatives, so the maths can no longer be collapsed. This is what allows the network to learn complex patterns.

Finally, Dropout randomly disables 10% of neurons during each training step. This can reduce overfitting and encourage patterns that generalise across cube states; it does not guarantee that the network will avoid memorisation.

The same sequence (Linear → BatchNorm → ReLU → Dropout) then compresses the 4096 values down to 2,048 neurons. This matches the size required by the following residual blocks.

The critical thing to understand is that the first layer of 4096 neurons moves beyond the 324 input values representing 54 stickers. These hidden activations do not have a predefined one-to-one mapping to the physical cube. They may represent colours, positions or more abstract combinations; without further interpretability work, we do not know exactly what they encode.

The network then has 4 residual blocks of 2048 neurons, the core layers of the 'black box' where learning takes place.

A residual block is a pair of layers with a skip connection. In a normal network, each layer passes its output only to the next layer. If that layer makes a poor transformation, the original information is lost. A skip connection solves this by adding the block's input directly to its output:

output = f(x) + x

That "+ x" is the skip connection. It has two benefits. First, if the layers have nothing useful to add, they can learn to output near-zero and the input passes through untouched — it is easier to learn what to change than what the complete answer should be. Second, it creates a direct highway for the learning signal to travel backward during training, helping to mitigate the vanishing gradient problem where signals fade to nothing in deep networks.

Source: He et al. — Deep Residual Learning

This is the single most important architectural decision in the network. The identity skip connections used here require the input and output to be the same size (2048), which is why the input projection compresses to 2048 before the residual blocks begin. Each block contains two linear layers, so our four residual blocks give us eight layers of processing, with an additional path for gradient flow.

Source: He et al. — Deep Residual Learning

Our next block is the Output Projection. It takes the 2048 outputs from the final residual block and compresses them down to 512 neurons, distilling the network's internal representation into a compact form for the two heads.

The final blocks are therefore our 2 heads, the Value Head (512 → 256 → 1 single value of 'moves until solved') and the Policy Head (512 → 256 → 12 raw scores for the next best move, which are converted to probabilities using softmax at inference time).

Training the network

The network now exists, but it knows nothing. The main weight matrices start from random initial values; some biases and normalisation parameters use fixed initial values. If we were to pass a scrambled Rubik’s cube through the network, it would output a random distance estimate and random move scores.

Source: PyTorch — BatchNorm1d

I tried two training approaches, but the one described here learns from scrambles generated backwards from the solved state. It was inspired by the DeepCube and DeepCubeA work at the University of California, Irvine. The original DeepCube introduced Autodidactic Iteration (ADI), and DeepCubeA used approximate value iteration and search. My description below uses scramble lengths and inverse moves as training labels; that alone is not the full ADI algorithm. The concept is simple: rather than using experts to label the data, we generate large volumes of it by working backwards from a solved cube.

Source: McAleer et al. — Autodidactic Iteration · Agostinelli et al. — DeepCubeA, 2019

The logic is as follows: Start with a solved cube. Apply a random move. The cube is now 1 move from solved. Apply another random move. The cube can now be solved in at most 2 moves; those moves might also cancel. Keep repeating this for 20 moves, record the final cube state, the number of moves (the distance label), and the inverse of the last move (a valid first move for retracing the scramble, though not necessarily an optimal one).

The network was trained with 20 million of these random samples with a scramble depth of up to 20 moves (The familiar 20-move bound counts a half-turn as one move. With the 12 quarter-turn actions used here, the corresponding bound is 26, so this training set does not cover every cube state.)

Source: Rokicki and Davidson — 26 quarter turns, 20 half turns

The Training Loop

Each training step followed the same four-stage process:

  • Forward pass — feed a batch of cube states through the network and collect the predictions.
  • Loss calculation — compare the predictions against the training labels using MSE for the value head and cross-entropy for the policy head (as described in the previous section).
  • Backward pass — calculate how much each parameter contributed to the error. This is backpropagation, and PyTorch handles it automatically.
  • Update — adjust every parameter slightly in the direction that reduces the error. This is handled by the optimiser.

PyTorch handles backpropagation, the gradient calculations, and the optimiser performs the parameter updates. The complexity is hidden inside loss.backward() which traces back through all 15 layers and 44.6 million parameters.

The ‘Adam’ optimiser adapts the learning rate for each parameter individually: it uses moving averages of gradients and squared gradients to scale each update. The initial learning rate was 0.001 and it halved every 10 epochs, gradually reducing the step size as the network got closer to a good solution.

Source: Kingma and Ba — Adam

Scale and Duration

The training ran on the DGX Spark (GB10 GPU). The 20 million training samples were divided into batches of 1024 cubes and fed through the network repeatedly.

One complete pass through all 20 million samples (an epoch) took about 25 minutes. The network was trained for 100 epochs, meaning every one of the 20 million training cubes was seen by the network 100 times. In total, the network processed 2 billion cube states during training (sounds like a lot, but remember the 43 quintillion number we are up against!).

The entire training run took approximately 42 hours.

Results

Every 10 epochs, we paused training and tested the network on 100 freshly scrambled cubes at different difficulty levels. The results at epoch 10 (the best checkpoint):

The network quickly solved all the easy cubes in these tests (5 and 10 moves). For harder scrambles it struggled — 37% on cubes generated by 20-move scrambles was the best that I achieved.

Source: Rokicki and Davidson — 26 quarter turns, 20 half turns

One interesting observation: the best results on 20-move cubes came at epoch 10, not at epoch 100. The total loss continued to fall throughout training (from 8.64 to 5.05) but the solve rate on the hardest cubes did not improve. The value loss dropped steadily (6.99 -> 3.62), meaning predictions better matched the scramble-length targets, but the policy loss barely moved (1.65 -> 1.43), meaning the loss for the labelled moves improved more slowly; the two loss scales are not directly comparable.

One possible interpretation is that fitting the distance labels was easier than predicting the sampled inverse move. That needs further testing, since scramble labels can be noisy and several next moves may be useful. Intuitively, predicting "this cube is about 12 moves from solved" is an easier problem than predicting "the next move should be (F’)” from 12 possible options.

The benchmark solve rate and the physical robot trials used different sets of cubes, so they should be read separately. In practice, the beam search algorithm (which explores multiple possible move sequences in parallel) compensates for imperfect move predictions, and the robot successfully solved 19 out of 19 cubes during testing.

The result looks identical to the original robot that uses the simple scan -> solve Python programme, and achieves the same result.

However, here’s the thing… despite all the explanation and theory above, I have not established which internal features the JoeCube44m neural network uses to guide the search. I fed a neural network with 324 numbers, showed it 20m example cubes with one single next move and a scramble-length target, and it learned. Did it learn the algorithms that human experts like Teodor Zajder use to solve cubes? I have not tested that. Remember, we supplied the cube’s sticker encoding and move rules, but no hand-written solving algorithms. The network successfully solved all 19 of the cubes I scrambled using patterns it learned in layers of weighted numbers that I have not yet translated into a human-readable explanation.

And this is why I will never look at my mindcuber robot the same again.
