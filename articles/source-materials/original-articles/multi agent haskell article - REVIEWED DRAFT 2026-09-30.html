Introduction to Haskell

I was introduced to Haskell by a tutor leading a CS course 'Algorithms and Data structures'. Despite the fact that 9 months of course material was all written using Python, the tutor opened the first lecture by dismissing it as rubbish and proceeded to teach the entire course using Haskell. After a very confusing first couple of months (no familiar mutable variables or conventional loop counters and a compiler stricter than a Dickensian headmaster), supplemented by a few hundred quid on World of Books, the penny dropped. Haskell is cool! It made me think differently, and that was reason enough to keep learning.

Source: Haskell — Input/Output and imperative programming

Haskell is a purely functional programming language. The basic adage is, a Haskell programme describes what result you want, rather than specifying how to compute it step by step. It is statically typed with powerful type inference and immutable values in pure code: a pure function applied to the same arguments has the same result, while I/O may depend on the outside world. The initial learning challenge is learning alternatives to mutable loop counters, such as recursion, folds and traversals. This drives a completely different way of thinking to structure functions based on recursion. The result being, arguably, actually quite elegant!

Source: Haskell — Input/Output and imperative programming

insertionSort :: Ord a => [a] -> [a]
insertionSort [] = []
insertionSort (x:xs) = insert x (insertionSort xs)
  where
    insert :: Ord a => a -> [a] -> [a]
    insert x [] = [x]
    insert x (y:ys)
      | x <= y    = x : y : ys
      | otherwise = y : insert x ys

This example of insertionSort gives us a constrained polymorphic function that will work for any type 'a' that has an Ord instance (for example Int, Integer, Char, String, or suitable Maybe and custom algebraic data types). Note the recursion (and nested recursion) and the two base cases which end the recursive loop. The notation (x:xs) is simply the head (x) and the rest (tail xs) of the list. Now tell me that’s not neat!

Although Python dominates the AI landscape, Haskell's strengths align well with the challenges of agent orchestration. In a multi-agent system, messages flow between components with specific structures. The record type documents the fields expected by the program and catches many type mismatches. It does not validate arbitrary incoming JSON or the meaning of a message; parsing, validation and error handling are still needed.

The idea for the app was to create 3 agents and 1 facilitator using different LLMs and trigger a debate between them (yes this has been done a million times before I am sure, but perhaps not with Haskellian agents!). I used a custom message format inspired by A2A, passing JSON files between agents and converting them to Ollama’s prompt format. This is not a conformant implementation of the A2A protocol.

Source: Agent2Agent — protocol specification

Handling Impure Operations

But wait! LLM calls are impure! They perform network I/O and may produce different responses on different calls, so we need to break out of the pure world and talk to the real world. Haskell does this using the IO monad. Have a look at the function used to call Ollama:

Source: Haskell — Input/Output and imperative programming

-- Request-construction excerpt from the body of callOllama.
-- Sending the HTTP request and parsing the response are omitted.
manager <- newManager tlsManagerSettings
let ollamaMsgs = toOllamaMsgs agentCardText history
let reqBody = OllamaRequest
      { model = modelName
      , ollamaMsgs = ollamaMsgs
      , stream = False
      }
  • IO is the monad here, it describes the I/O actions that the runtime executes. The 'do' notation lets you sequence these actions. The syntax does feel imperative: it sequences I/O actions while keeping those effects separate from pure code.
  • The manager utility is from the haskell lib Network.HTTP.Client which is pretty much the same as the requests lib in Python.
  • toOllamaMsgs calls a function that converts the A2A message to Ollama's format.
  • agentCardText contains the persona text I pass to the model, inspired by an agent description. A standard A2A Agent Card is structured service metadata. These agents currently have no tools; I found Python’s ecosystem easier for experimenting with Model Context Protocol (MCP) integrations.
  • history is the cumulative history of the debate, so that the agents can make arguments with context.

Managing State in the Agent Cafe

The Agent Cafe as the programme is called, simulates 5 rounds of debate between 3 personalities (A philosopher, an economist and the CEO of a large enterprise). The orchestration requires managing state, in this context, keeping track of the rounds, whose turn it is, and the history of the conversation. This is easy in Python, and actually not too complex in Haskell. Haskell provides a library mtl (Monad Transformer Library) which provides abstractions for effects, including state threading via StateT.

-- Opening of agentTurn; the full excerpt follows below.
agentTurn :: Agent -> MessageType -> Debate ()
agentTurn agent mType = do
    state <- get

For a debate stack such as StateT DebateState IO, state operations work as you would expect; it has functions get, put, modify and liftIO, the last of which allows us to run I/O operations within the Debate monad.

Source: Haskell mtl — StateT

get :: Debate DebateState
-- Returns the current state

put :: DebateState -> Debate ()
-- Replaces the entire state

modify :: (DebateState -> DebateState) -> Debate ()
-- Applies a function to transform the state

Here's how each agent takes their turn in the debate using the above

agentTurn :: Agent -> MessageType -> Debate ()
agentTurn agent mType = do
    state <- get
    -- Generate a response from the agent
    liftIO $ TIO.putStrLn $
        "... " <> agentName agent <> " is thinking ..."
    msg <- liftIO $ agentRespond agent mType state
    -- Update the state with the new message
    modify (\s -> s { messages = messages s ++ [msg] })
    -- Print the message
    liftIO $ printMessage msg

Calling the main function

-- Excerpt: helper types, imports and functions are defined elsewhere.
main :: IO ()
main = do
    let initialState = emptyDebateState defaultTopic defaultRounds
    (_, finalState) <- runStateT runDebate initialState
    saveTranscript finalState

defaultTopic :: Text
defaultTopic = "How will AI impact the world over the next 10 years?"

defaultRounds :: Int
defaultRounds = 5

-- saveTranscript writes the final state to debate_transcript.json.
-- Its implementation is not included in the source article.

This creates a debate containing the topic, an empty message list and a round counter set to zero. The key line is (_, finalState) <- runStateT runDebate initialState. It returns an action result and the final state. The _ discards the unit value () returned by runDebate :: Debate (); finalState contains the accumulated debate state, including the transcript. saveTranscript finalState then saves it.

The Agents & LLMs

Part of the idea of the project was to get 3 different open-weight models running on the Spark, which proved... remarkably easy. Ollama really does make running models straightforward. The config was as follows:

  • Philosopher - Qwen 2.5 32B
  • CEO - Llama 3.1 70B
  • Economist - Gemma 2 27B

Inference was quick (I didn't time exactly) and there were no resource issues, so not really a test of the Spark, more a utilisation of its memory for a short period of time.

So.... What Happened?

Initially, something very weird but equally fascinating. My original design had a 'Barista' agent whose job it was to introduce the debate topic, which was prompted as

How will AI impact the world over the next 10 years?

Everything worked, except the barista went off-topic and introduced a debate in Arabic about ancient Rome "From the platforms and public facilities of the forum".

I quickly decided to disempower him as a host and pass more explicit prompts directly to the 3 debate participants, essentially hardcoding it.

The debate was actually interesting, so it may become an article of its own. Here is the opening gambit from the Philosopher:

Philosophically, we must question whether the integration of AI aligns with Aristotelian ideals of eudaimonia—human flourishing—or if it leads to a form of instrumentalism where individuals are seen merely as data points for optimization. The Kantian notion of treating individuals as ends in themselves, rather than means to an end, is particularly relevant here. If AI systems make decisions that override human autonomy or if they perpetuate biases embedded within their training data, we risk undermining the dignity and rights of individuals.

The programme is remarkably short and simple. I hope to publish it too; building it has given me a much better feel for Haskell’s strengths and rough edges.
