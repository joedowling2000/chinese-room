An explanation and demonstration of LLM quantization using the Mixtral 8 x 7b MoE model, with a bit of maths, benchmarks and an ending that will require a sequel...

This weekend's hobby project is something I have been keen to try for a while, exploiting one of the bleeding-edge features of the GB10 chip, NVFP4, with the 'bleeding-edge' bit ultimately coming back to bite me when trying to test the results.

The project may sound complex on the face of it, but is actually relatively simple to execute and explain;

Transformer-based LLMs are built on the transformer architecture and consist of the following layers:

1. Embedding layers - which convert text tokens into numerical vectors.

2. Attention mechanisms - which allow the model to focus on relevant parts of the input.

3. Feed-forward networks - which process and transform these representations.

4. Output layers - which predict the next token.

Each of these components contains millions or billions of weight parameters. For example, Mixtral 8 x 7B contains approximately 46.7 billion parameters in total, including shared components and eight experts in each feed-forward layer. These parameters are stored as floating-point numbers and the original Mixtral 8x7B checkpoint used here is distributed in BF16 format.

Source: Mistral — Mixtral of Experts

Each BF16 parameter (16 bits) occupies 2 bytes. For a 46.7-billion-parameter model like Mixtral, 46.7 billion × 2 bytes = 93.4 GB, or about 87.0 GiB. Those are two units for the same amount of data, not a range of memory requirements. Runtime memory also includes the key-value cache, activations, workspaces and software overhead.

This presents a practical problem. GPU memory varies widely; many consumer cards have 8–24 GB, and even high-end workstations struggle to run these models efficiently. Even the DGX Spark, a purpose-built edge device, has 128GB, so loading Mixtral as distributed is really pushing the limits. (Side muse... The solution (other than buying more hardware) is quantization; the process of reducing the precision of model weights from higher-bit representations (like BF16) to lower-bit representations (like INT4 or NVFP4). The goal is to dramatically reduce memory requirements while minimizing the impact on model quality.

Linear Quantization

In its simplest form, linear quantization maps continuous floating-point values to a discrete set of values that can be represented with fewer bits. The simplest form of quantization maps floating-point values to integers using a linear transformation:

q = round (x / scale)

Where:

q is the resulting quantized integer

x is the original floating-point value

scale determines the step size between quantized values (see below!)

For example, an 8-bit integer has 256 bit patterns, but this symmetric example uses 255 values (−127 to +127), leaving −128 unused. A model might have weights in the range (-1.0, 1.0) that we want to quantize to 8-bit signed integers (-127, 127) to fit in our 255 8-bit range.

To calculate the scale value:

scale = (max_val - min_val) / (255 - 1)

scale = (1.0 − (−1.0)) / 254 = 1/127 ≈ 0.00787402

Using this, to quantize a value of 0.5:

q = round(0.5 / (1/127)) = round(63.5) = 64

if we dequantize back:

dequantized = 64 / 127 ≈ 0.50393701

The absolute quantization error is |0.5 − 64/127| ≈ 0.00393701.

In other words, we have halved the raw weight storage compared with BF16, before scale metadata and any tensors left at higher precision. This particular weight has an absolute error of about 0.00394; the effect on a whole model must be measured. Even at 8 bits, Mixtral’s raw weights take about 46.7 GB (43.5 GiB), which is still beyond many consumer GPUs.

4-bit Quantization - The Challenge!

Four bits have 16 bit patterns. For a symmetric integer example I will use −7 to +7 (15 values), leaving −8 unused. The range [−1.0, 1.0] now has:

scale = 1/7 ≈ 0.14285714

Therefore, for the same example weight of 0.5:

q = round(0.5 / (1/7)) = round(3.5) = 4

dequantized = 4/7 ≈ 0.57142857

The absolute error is |0.5 − 4/7| ≈ 0.07142857, about 18 times the 8-bit error in this example. The raw weight payload is one quarter of BF16, but scale metadata and tensors retained at higher precision reduce the actual compression. Whether quality remains acceptable needs to be tested. These examples use integer quantization; NVFP4 is a different format.

Source: NVIDIA — Introducing NVFP4

The Project!

Mixtral 8x7B Instruct is a MoE model whose BF16 weights (about 87 GiB) is large enough to demonstrate quantization benefits whilst just squeezing onto a SINGLE DGX Spark! The 'Mixture of Experts' architecture provides an interesting test case.

The MoE architecture means at each feed-forward layer, 2 of the 8 experts are selected for each token, making the effective parameter count during inference closer to 13B, however, a fully resident inference setup still needs storage for all 46.7B parameters.

Source: Mistral — Mixtral of Experts

Benchmarking - Quality (Perplexity)

The perplexity benchmark evaluates Mixtral's ability to predict tokens in a held-out text corpus. A lower score means higher average probability assigned to the observed tokens under the same evaluation setup; it is not a direct measure of understanding. This is a key test for our quantization; we want to see gains in speed and size reduction, without increasing the perplexity score.

Source: Hugging Face — Perplexity of fixed-length models

Again, Hugging Face provides a script which loads the WikiText-2 test set from the datasets library. It performs the following steps;

1. First it concatenates all the text into a single string and tokenizes it.

2. For each window (size 2048 tokens), extract a chunk of input tokens.

3. Predict the likelihood of the next tokens, and calculate the prediction errors (or negative log-likelihood -NLL).

4. Finally, calculate the token-weighted mean negative log-likelihood and exponentiate it: perplexity = exp(mean NLL) (more detailed explanation here https://huggingface.co/docs/transformers/perplexity).

Source: Hugging Face — Perplexity of fixed-length models

Quantization

The NVFP4 quantization process uses NVIDIA Model Optimizer (ModelOpt). The excerpt below shows the calibration forward loop; it does not include the actual quantization and checkpoint export calls.

Source: NVIDIA Model Optimizer — post-training quantization

Calibration forward-loop excerpt; quantization and export omitted in the original

import modelopt.torch.quantization as mtq
from modelopt.torch.export import export_hf_checkpoint
calibration_data = load_calibration_samples(tokenizer,
                                           num_samples=512)
def forward_loop(model):
    model.eval()
    with torch.no_grad():
        for batch in calibration_data:
            model(input_ids=batch["input_ids"],
                  attention_mask=batch["attention_mask"])

NVFP4 is not uniform INT4: it stores E2M1 floating-point values with an FP8 scale for each block of 16 values and a further FP32 scale. The block scales bring storage to roughly 4.5 bits per quantized value before other overheads. For the format and calibration workflow, see NVIDIA’s NVFP4 explanation and Model Optimizer documentation in the sources below.

Source: NVIDIA — Introducing NVFP4 · NVIDIA Model Optimizer — post-training quantization

The quantized checkpoint was exported! The output model reduced in size broadly in line with expectations. But when coming to load the quantized model into memory the dependency errors started...

After 30 minutes of searching and hacking around, Gemini pointed me towards a likely explanation: the packed checkpoint needed compatible runtime support. That was a useful lead, rather than independent proof of the diagnosis.

The practical issue was compatibility between the checkpoint format, the inference runtime, its kernels and this GPU. The failures below describe the software versions I used at the time; they are not a statement that current versions cannot run NVFP4.
